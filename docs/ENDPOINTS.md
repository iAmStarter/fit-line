**Phase 0 note:** code surface is live (`doPost` verifies + returns 200); the deployed `/exec` URL + LINE webhook wiring are owner-only manual steps (clasp login + LINE console) — statement, not a blocker.

**Phase 1 note:** doPost now routes image events end-to-end on the mock OCR (`ocrMock`). No new deployed URL — the `/exec` webhook is the same surface, its behaviour expanded. Outbound LINE calls added: `GET api-data.line.me/v2/bot/message/{id}/content` (getContent) and `POST api.line.me/v2/bot/message/reply` (reply), both Bearer `LINE_CHANNEL_ACCESS_TOKEN`, `fetchTimeoutSeconds: 10`.

**Phase 2 note:** doPost now also handles the confirm `postback` → Sheet write. No new deployed URL — same `/exec` webhook, behaviour expanded to the write path. New datastore access: `SpreadsheetApp.openById(SHEET_ID)` → tabs `submissions` (14-col, write-by-header-name) + `employees` (3-col, register-once upsert); CacheService stash consumed on success (`removeSubmission`). Outbound reply reuses the Phase 1 LINE reply seam.

**Phase 3 note:** anti-spam guards added — no new deployed URL, same `/exec` webhook. Image path now runs two cost gates BEFORE OCR: (1) per-user rate-limit via `CacheService` counter `rl:<userId>` (get→+1→put TTL 60s; 5th passes, 6th blocked) and (2) system-wide sha256 image dedup via `Utilities.computeDigest(SHA_256)` + `sheetRepo.imageHashExists` scan (byte-identical resend/share → reject, OCR spy = 0). Confirm postback now idempotent under LINE redelivery: `LockService.getScriptLock().waitLock(10000)` wraps `submissionExistsByMessageId(messageId)` check-then-write (duplicate messageId → skip write, echo success); waitLock timeout → "ระบบไม่ว่าง ลองใหม่" (no double-write). imageHash now threaded stash→row (was `''`). Privacy: only the hash is stored, never the image.

**Phase 4 note:** business-rule pipeline landed — no new deployed URL, same `/exec` webhook. The image path now runs `evaluateSubmissionRules(metrics, userId, todayISO)` post-OCR: (1) `calorieRule` (Phase 1), then (2) `backdateRule` — activityDate (date-only, Asia/Bangkok) must be today or yesterday; future → "วันที่กิจกรรมไม่ถูกต้อง", older than yesterday → "วันที่กิจกรรมเก่าเกินกำหนด (ย้อนหลังได้ ≤ 1 วัน)", null/unreadable → "อ่านวันที่จากรูปไม่ได้ ส่งรูปที่เห็นวันที่ชัด" (no silent pass), then (3) `dedupDateRule` → `sheetRepo.hasRecordedSubmission(userId, dateOnly)` scans `submissions` for a row matching userId + activityDateISO + status=`recorded` (rejected rows never block) → "วันนี้บันทึกไปแล้ว". Pipeline short-circuits at the first failing rule (deterministic reason; e.g. low-calorie AND too-old rejects on calories) and does NOT scan the Sheet when an earlier rule already failed. Rules are pure (no `new Date()` inside — `todayISO` injected by main). No new datastore surface: reuses the Phase 2 `submissions` read-by-header-name scan.

**Phase 5 note:** summary + native bar chart + admin-dispute log — no new deployed URL, same `/exec` webhook, behaviour expanded. (1) **Success card** now carries a summary line "สัปดาห์นี้ N · เดือนนี้ N · รวม N" (recorded-only tallies; week = Monday→today of the Asia/Bangkok week, month = current `yyyy-MM`, total = all-time) + a **native-Flex bar chart** (7 vertical Flex boxes, height ∝ value normalised to the series max, 0-day at a visible baseline, per-bar numeric label — **no external image URL**, privacy-safe). Aggregates come from `sheetRepo.countSubmissions(userId, todayISO)` + `recentDailyValues(userId, todayISO)` (scan `submissions` filtered userId + status=recorded; `todayISO` injected by main via `Utilities.formatDate(now,'Asia/Bangkok','yyyy-MM-dd')`), computed AFTER the insert so the new row counts. (2) **Dispute log:** a new `disputes` tab (`messageId, userId, activityType, reason, disputedAtISO`) — `postback` `action=dispute&mid=<messageId>` → `sheetRepo.logDispute(mid, userId, '', 'user-dispute')` appends **1 row per messageId** (idempotent via `disputeExistsByMessageId`; a missing/empty `disputes` tab → graceful no-crash) → replies a neutral ack card "ส่งเรื่องให้แอดมินตรวจสอบแล้ว". The reject-card dispute affordance (`buildRejectCard(m, reason, { disputeMessageId })` → "แจ้งแอดมิน" postback quick reply) + the `disputeGuard` fail-counter (`fc:<userId>:<activity>`, threshold 3) are implemented + unit-tested, and the **auto-offer is now wired into the synchronous image-reject path**: on a post-OCR RULE reject, `handleImageMessage` calls `bumpFailCount(userId, metrics.activityType)` (per-(user, activity) counter — `run`/`ride` independent) and, when `shouldOfferDispute(count)` (count ≥ 3), passes `disputeMessageId = messageId` so the 3rd same-activity reject card carries the "แจ้งแอดมิน" quick reply (`action=dispute&mid=<messageId>`). The bump fires ONLY on post-OCR rule rejects — pre-OCR block paths (rate-limit / duplicate) return before it and touch no counter. Below threshold the card renders the Phase-1 shape (cameraRoll only). The prior frozen-router conflict was cleared by re-freezing `router.spec.ts` to mock `disputeGuard` (see docs/ISSUES.md, RESOLVED).

**Phase 7 note (FINAL):** real identity mapping + rich-menu trigger — no new deployed URL, same `/exec` webhook, behaviour expanded. (1) **Identity mapping:** a new `roster` tab (`userId, name`, read-by-header-name so a column reorder can't break the match) — `sheetRepo.resolveEmployeeName(userId)` looks up the sender's real name; the confirm write path uses it for the `submissions.name` cell AND `ensureEmployee(userId, resolveEmployeeName(userId))`, so a rostered user records their real name (`U1`→`สมชาย`). Every degraded case (missing `roster` tab, empty/header-only, missing column, userId not found, matched-but-empty name) falls back to `PLACEHOLDER_EMPLOYEE_NAME` (`(ยังไม่ระบุชื่อ)`) and NEVER throws — an unpopulated roster records the placeholder (graceful). Names are PII → they live in the Sheet only, never logged. (2) **Rich-menu trigger:** `richMenu.buildRichMenu()` returns the LINE rich-menu JSON — a full-width 2500×843 canvas split into 2 tappable postback areas: left "วิธีส่งรูป" → `action=help`, right "สรุปของฉัน" → `action=summary` (emoji-free). `richMenu.registerRichMenu()` = OWNER-run one-time setup (`POST https://api.line.me/v2/bot/richmenu`, Bearer `LINE_CHANNEL_ACCESS_TOKEN` from Script Properties, never logged) → returns `richMenuId`; NOT on the request path, NOT called at import time. (3) **Postback routing** (`handlePostback`): `action=help` → `buildTriggerCard()` (how-to "วิธีส่งรูป" + message-level `cameraRoll` quick reply); `action=summary` → the sender's own summary via `countSubmissions` + `recentDailyValues` → `buildSummaryCard(counts, daily)` (info/neutral "สรุปของฉัน" + "สัปดาห์นี้ N · เดือนนี้ N · รวม N" line + native-Flex bar chart, **no external URL**); `action=confirm&id=…` → unchanged write path → terminal "บันทึกแล้ว" success card (the running week/month/total tally now lives behind the "สรุปของฉัน" button, NOT on the write-path card); any unknown `action` → graceful ignore (no reply, doPost stays 200). **Deploy:** `/exec` URL + LINE webhook + rich-menu register are owner-only manual steps (clasp deploy · LINE console) — staged/manual, a statement not a blocker.

**Phase 8 note (CR-1 — auto-save, no confirm):** the 2-tap confirm step is REMOVED. A passing image now writes to `submissions` IMMEDIATELY on the image path (`handleImageMessage`) and replies the success card in ONE event — no confirm card, no `action=confirm` postback write. The Phase-3 messageId + `LockService` idempotency (`withScriptLock` + `submissionExistsByMessageId`) MOVED from `handlePostback` ONTO the image write path (a webhook redelivery of the image now writes directly, so the lock/dedup guards it there — exactly 1 row). Employee upsert + `resolveEmployeeName` run inline; the running summary (counts + bar chart) is computed AFTER the auto-insert. `handlePostback` keeps dispute/help/summary; a legacy `action=confirm&id=…` (old card still in a chat) is a graceful silent no-op. **Deleted:** `src/line/flex/confirm.ts` (`buildConfirmCard`) + `src/state/cacheStore.ts` (`stashSubmission`/`retrieveSubmission`/`removeSubmission` — the cross-event stash is gone; `StashedContext` type moved into `src/types/ocrMetrics.ts`). Reject/rules/dedup/rate-limit/OCR/identity/rich-menu unchanged. No new deployed URL — same `/exec` webhook, behaviour changed. Security re-threat-model: OCR misread now auto-records (mitigation: rule pipeline still gates every save; no manual value edit); redelivery double-write mitigated by the moved image-path lock (mandatory); postback `id`-tamper surface reduced. **NOTE:** one frozen test (`test/phase-3/imageGate.spec.ts` boundary) conflicts with the CR-1 auto-save + system-wide imageHash dedup — see docs/ISSUES.md (OPEN, needs test-author).
